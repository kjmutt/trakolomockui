Application architecture
Reference architecture for building Trakolo as a real product — multi-tenant, subdomain-routed, sized for 10,000 concurrent users. Not part of the product itself; internal engineering documentation.
Entity relationships → View db/schema.sql → View db/schema-master.sql →
In one line
One modular-monolith app fleet behind wildcard subdomains, a database-per-tenant data tier — every cloud tenant gets its own Postgres database, resolved through the separate trakolo-master control-plane database — and background services split by job type so one failure never takes down every job for every customer.

Layer walkthrough
①Edge & routing
One wildcard DNS record and TLS cert cover every tenant subdomain. portal.trakolo.com is the tenant-agnostic sign-in chooser — the same job login.html does in this mockup.
Wildcard DNS · *.trakolo.com Load balancer + wildcard TLS portal.trakolo.com — sign-in

②API Gateway
Every request for apps/api — whether from the SPA's own fetch calls or a third-party REST integration — passes through one gateway, not a direct path to the app fleet. This is the layer that actually answers "is there an API gateway": yes, and it's where auth, per-tenant rate limits, and versioning live, not scattered across modules. See Release & DR for how a new API version rolls out without breaking existing integrations.
Routing — path-based to itsm/sam/dev/docs Auth — OAuth2 (user sessions) + API keys (integrations) Rate limits — per tenant, per plan tier Versioning — /api/v1, additive only Developer portal — the REST API docs, see API reference
▼
③App fleet — stateless, horizontally scaled
Shared compute pool for every tenant by default, including Enterprise — no per-tenant pinning, any instance serves any tenant's request once resolved. A compute_tier field on the tenant registry is the escape hatch: it can pin one contractually-demanding tenant to a dedicated pool without a second codebase. Each module (itsm/sam/dev/docs) is a project inside the ASP.NET Core solution with its own xUnit test project — one deployable, independently testable modules.
apps/web — React 18 (SPA) apps/api — ASP.NET Core 10: itsm apps/api — ASP.NET Core 10: sam apps/api — ASP.NET Core 10: dev apps/api — ASP.NET Core 10: docs compute_tier: shared (default) / dedicated (opt-in) xUnit — itsm.Tests · sam.Tests · dev.Tests · docs.Tests
▼
④Control plane
Resolves subdomain → core.tenants row in trakolo-master (see db/schema-master.sql) → that tenant's db_host + db_name + storage bucket, on every request — cached so tenant resolution never costs a database round-trip. trakolo-master is a database Trakolo owns and no tenant ever connects to; it holds the registry plus every table behind the Platform Admin console (plans, subscriptions, leads, campaigns, error log).
trakolo-master — core.tenants (slug → db_host, db_name, subdomain) Redis — tenant cache + sessions
▼
⑤Data tier
Every cloud tenant gets its own Postgres database (see db/schema.sql) — not a shared schema with row-level tenant_id scoping, a separate CREATE DATABASE per tenant, which Postgres treats as a hard isolation boundary on its own (no cross-database queries or foreign keys are even possible). By default many tenant databases share a physical Postgres cluster — cheap, and still fully isolated — with db_host in trakolo-master the only thing that changes to move one tenant onto its own dedicated cluster. A read replica isolates reporting from ticket-write traffic.
PgBouncer / RDS Proxy Postgres cluster — many tenant databases Dedicated Postgres cluster — opt-in per tenant Read replica — reporting Object storage — bucket + prefix per tenant
▼
⑥Background & specialized services
Split by job type into independent deployables — not one shared worker process. If webhook delivery crashes, SLA escalation keeps running for every customer; it doesn't take everyone down at once. Each job carries an idempotency key and dequeues with FOR UPDATE SKIP LOCKED-style locking so a redelivered message is a no-op, not a duplicate.
worker-sla — SLA escalation worker-rules — business rules engine worker-webhooks — delivery + retries worker-reports — export scheduler worker-ai-agent — separate service, different resource profile
▼
⑦Monitoring
The same health registry behind Admin → System status feeds real dashboards and alerts in production — now per worker, so a failure is attributed to one job type, not "background services" generically.
platform.services — health registry Dashboards + alerts, per worker

Tenancy models — what we chose, and what it costs
Five workable models, ordered by how much each tenant is isolated from every other. Isolation and cost-per-tenant move in the same direction: every step down this table buys a stronger guarantee and charges for it in idle infrastructure or operational fan-out.

Shared everythingA tenant_id column, checked by application code~zeroOne missing WHERE tenant_id = is a cross-tenant data leak. Retired — this is what the current design replaced.
Schema-per-tenantsearch_path, one database~zeroCatalogue strain: 500 tenants × 52 tables = 26,000 tables in one database, punishing autovacuum and planning.

Cluster-per-tenantThe Postgres instanceMedium — one managed instance eachCost. Only justifiable where a contract demands it.
Instance-per-tenantEverything — own app containers, own database, own cacheHigh — full stack always runningCost at the low end, and upgrades become a rolling campaign across N deployments.
These are not mutually exclusive — pick per plan tier
The registry already decouples routing from co-location, so one deployment can run several of these at once: Free/Team/Business on database-per-tenant over a shared cluster, Enterprise on instance-per-tenant with its own app containers, database, and region. core.tenants.compute_tier selects which, and db_host selects the cluster — both are one-row config changes, not a second codebase. The instance-per-tenant build is also the on-premise artifact (see Deployment options), so supporting it costs far less than it looks: it's the same image, hosted by us instead of the customer.
The constraint: connection pooling under database-per-tenant
A Postgres connection binds to exactly one database when it opens — there is no USE database. PgBouncer therefore keys its pools on (database, user), which means one pool per tenant, permanently, and no pool can ever lend a connection to another tenant no matter how idle it is. Database-per-tenant defeats connection pooling along exactly the axis pooling exists to solve.
Postgres backends are OS processes at roughly 5–10 MB each, plus shared structures that scale with max_connections; the realistic tuned ceiling is 400–1000. Against that, 500 tenants at a default_pool_size of 10 wants 5,000 server connections. What rescues the arithmetic is that tenants are not all busy at once — B2B service-desk traffic is working-hours shaped, so if 15% are concurrently active you need ~375, which fits. The real capacity limit is peak concurrent tenants, not tenant count — and a customer base spread across time zones behaves very differently from one where everybody opens their laptop at 09:00 in the same country.
min_pool_size must be 0
It keeps connections warm per pool. Set it to 2 across 500 tenant databases and 1,000 connections sit held and idle before a single request arrives. Accept the cold-start latency on a tenant's first query instead.
transaction mode constrains the app
Session mode pins a server connection per client and destroys the ratio, so transaction mode is mandatory — which rules out LISTEN/NOTIFY, session-level SET, cross-transaction advisory locks, and temp tables. Workers use Service Bus queues rather than LISTEN/NOTIFY for exactly this reason.
Alert on maxwait, not CPU
PgBouncer's SHOW POOLS exposes cl_waiting and maxwait. Any sustained maxwait above zero means pool starvation, and the next traffic bump will hurt. Database CPU will look fine right up until it doesn't.

Planning number — write this down and test it early
Budget a few hundred tenants per Postgres cluster, with the binding constraint being 50–100 concurrently active tenants. Load-test that ceiling well before there are that many paying customers, because the failure mode is a cliff rather than a slope: everything is healthy, then connection exhaustion hits and every tenant on the cluster fails at once. Schema-per-tenant would largely dissolve this problem by letting connections be shared — the pooling cost is the deliberate price of choosing a boundary the database enforces itself.
Platform capabilities the diagram above doesn't show
Four cross-cutting concerns that don't belong to any one module, and that get built badly — three or four incompatible times over — if they aren't named as platform capabilities up front.
Transactional outbox
Background workers being idempotent solves redelivery, but not the dual-write problem underneath it: commit a ticket to Postgres, then publish TicketCreated to Service Bus, and any crash between the two leaves the database updated and the message gone. No amount of consumer-side idempotency recovers an event that was never sent.

Write the event to an outbox table inside the same transaction as the business data, then let a dispatcher poll and publish it. The commit is atomic, so the event either exists with the data or neither does. Consumers still need idempotency for the at-least-once redelivery this produces — the two mechanisms solve different halves.
One workflow engine, not four
SLA timers, business rules, change approvals, access requests, catalogue fulfilment, and document sign-off all need the same primitives: conditions, assignment, timers, escalation, human tasks, retry, and an execution history you can audit.

Today itsm.sla_policies and itsm.business_rules are separate mechanisms with separate workers, and itsm.change_approvals is a third path. That's three implementations of "wait for a condition, then act" which will drift. A shared workflow module — definition, version, instance, step, human task, timer, transition, history — lets a service request and an asset disposal run the same engine. Build a constrained state machine first; an external BPMN engine can go behind the same interface later if it earns its complexity.
Search is undefined and needed everywhere
Knowledge articles, wiki pages, documents, tickets, assets, and the command palette all need retrieval, and nothing in the current design says how. Start with PostgreSQL full-text search — it is genuinely sufficient at single-tenant volumes and removes a whole component from the on-premise stack. Move to OpenSearch only when relevance tuning or cross-module ranking demands it, behind an ISearchProvider so the switch isn't a rewrite.

Indexing belongs in its own worker fed by the same outbox events, not inline with the write path — a slow index must never fail a ticket save.
AI reads through permissions, never around them
The AI agent must not query operational tables directly. Retrieval runs through the same authorisation context as a human request, so a copilot can only surface what that user could already open, and actions execute as ordinary application commands rather than direct writes. Anything else turns the assistant into a permission bypass with a friendly interface — and in a tenant database holding another company's incidents, that is the single worst failure mode available.
One image, three deployment profiles
The same container images, the same migrations, and the same release version serve cloud and on-premise. Deployment differences are configuration and infrastructure adapters, never a second codebase — which is what keeps the instance-per-tenant tier in the table above nearly free to support.

The adapter boundary has to hold at the semantic level
An interface that leaks its cloud implementation isn't portable. Service Bus session locks and RabbitMQ consumer acknowledgements are not the same delivery model, so IMessageBus must expose the guarantee both can honour — at-least-once with an idempotency key — rather than the richer semantics of whichever one gets built first. The same applies to expand-and-contract migrations: on-premise customers upgrade on their own schedule, so every migration must leave the previous application version able to run against the new schema. Add structures, ship code tolerant of both shapes, backfill, and only drop the old columns a release later.
Things this design depends on
Route everything through trakolo-master
No service hardcodes which database, bucket, or compute pool a tenant lives in — every lookup goes through trakolo-master's tenant registry. That's what makes "pooled cluster for most, dedicated cluster for one" a config difference (one row's db_host) instead of two codebases.
Sharing a physical cluster still shares fate
Separate databases stop one tenant's data from ever mixing with another's, but tenants whose databases sit on the same physical cluster still share connection pool, disk I/O, and query load. Per-tenant rate limits and the reporting read replica exist specifically to stop one noisy tenant from becoming everyone else's incident.
One worker, one failure domain
Splitting background jobs by type means a crash, a bad deploy, or a stuck queue in one worker is contained to that job — the lesson from the previous design, where one shared worker process going down stopped every background job for every customer at once.
