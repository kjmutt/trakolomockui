Deployment options
Which setup fits which customer — SaaS, Enterprise, or on-premise — and what it would take to move past the modular monolith if a single deployment ever needs true microservices independence.
Cloud hosting → System requirements →
In one line
Every cloud customer — Free through Enterprise — gets its own Postgres database from day one, routed to by the trakolo-master control-plane database; move a tenant onto its own dedicated physical cluster (still the same modular-monolith app) the moment a contract requires it. Reserve on-premise for air-gapped or data-residency requirements the cloud genuinely can't satisfy. Full microservices-on-Kubernetes is a real, documented option below — held in reserve for the 50,000-concurrent-user inflection point already flagged in System requirements, not adopted today.

Cloud, pooled physical cluster (default). Cheapest, fastest to onboard — and each tenant already has its own dedicated Postgres database, so isolation doesn't depend on getting a query-level filter right. See Entity relationships.

Cloud, dedicated physical cluster. Same app, same release train, same on-call — only this tenant's already-dedicated database moves off the shared cluster onto its own. A trakolo-master config change (db_host), not a fork.

On-premise perpetual license — no Trakolo-hosted subdomain or database at all. install/docker-compose.yml plus offline .trklic activation — see the Standalone section of Cloud hosting.
If you outgrow the modular monolith — microservices on Kubernetes
Not what's recommended today — Application architecture's modular monolith is justified by 70 real foreign keys within a single tenant's database, including tickets ↔ backlog items pointing at each other directly. Splitting that into services means distributed transactions across a genuinely tight data model. This is what it would look like if a single deployment ever needed independent per-module scaling or release cadence badly enough to accept that cost — held in reserve for the 50,000-concurrent-user inflection point in System requirements, not a current plan.
Orchestrator choice does not fix duplicate-job bugs
Duplicate tickets/transactions from a background worker are caused by two replicas of the same worker processing the same message at once — a data-layer correctness problem, not a scheduling one. Kubernetes doesn't know or care whether a job is idempotent; it just runs more copies of whatever container you give it. Moving worker-webhooks from Container Apps to AKS without changing the job-processing code would reproduce the identical bug on a different scheduler. What actually prevents it — already required by Application architecture's background-services layer regardless of where it runs — is an idempotency key per job (job_type:{tenant_id}:{entity_id}:{date}) plus safe concurrent dequeue (FOR UPDATE SKIP LOCKED for a Postgres-backed queue, or Service Bus sessions/message locks). Container Apps already autoscales each of the 5 workers independently via KEDA on queue depth — the same engine AKS would use underneath — so neither scaling nor duplicate-prevention is a reason to move workers to AKS on its own.
