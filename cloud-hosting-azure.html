Cloud hosting
Where each layer of the application architecture actually runs — a managed-Azure reference stack, an AWS comparison for the layers that are cloud-agnostic, and the standalone on-premise install for the perpetual-license edition.
Application architecture → View db/schema.sql →
In one line
Same six layers as the application architecture, mapped onto managed Azure services — Front Door at the edge, Container Apps for the fleet and the five job-type workers, Flexible Server hosting one dedicated database per tenant, Service Bus for background dispatch. Nothing about the app changes; only which cloud runs it.

Layer walkthrough
①Edge & routing
Front Door terminates a wildcard managed TLS cert and load-balances to the app fleet — CDN, WAF, and global routing in one resource, where AWS splits the same job across ALB/CloudFront.
Azure DNS · *.trakolo.com Front Door — managed TLS + WAF portal.trakolo.com — sign-in
▼
②API Gateway — Azure API Management
Front Door hands API traffic to APIM before it ever reaches Container Apps — this is the explicit "is there an API gateway" answer: yes. APIM owns routing to itsm/sam/dev/docs, OAuth2/API-key auth, per-tenant rate limits, /api/v1 versioning, and the developer portal that publishes the REST API docs (see API reference).
Routing — path-based to itsm/sam/dev/docs Auth — OAuth2 (user sessions) + API keys (integrations) Rate limits — per tenant, per plan tier Versioning — /api/v1, additive only Developer portal — REST API docs
▼
③App fleet
Static Web Apps serves the React 18 SPA; Container Apps runs the ASP.NET Core 8 API as a modular monolith, scaling on HTTP load via KEDA. Shared compute pool for every tenant by default — compute_tier pins a rare contractually-demanding tenant to a dedicated Container Apps environment without a second codebase. Each module carries its own xUnit test project.
Static Web Apps — apps/web (React 18 SPA) Container Apps — apps/api (ASP.NET Core 8: itsm · sam · dev · docs) compute_tier: shared (default) / dedicated (opt-in) xUnit — itsm.Tests · sam.Tests · dev.Tests · docs.Tests
▼
④Control plane
Same Redis protocol as the AWS reference — the trakolo-master cache client code doesn't change between clouds.
trakolo-master — core.tenants (slug → db_host, db_name) Azure Cache for Redis
▼
⑤Data tier
Azure Database for PostgreSQL Flexible Server, zone-redundant HA, fronted by a PgBouncer sidecar — one dedicated database per tenant (see db/schema.sql), pooled onto a shared Flexible Server by default with a dedicated Flexible Server available per tenant on request, and a read replica isolating reporting from ticket-write traffic.
PgBouncer sidecar Flexible Server — many tenant databases, zone-redundant HA Flexible Server — dedicated, opt-in per tenant Read replica — reporting Blob Storage — container + prefix per tenant
▼
⑥Background & specialized services
Five independent Container Apps jobs, each with its own Service Bus queue — not one shared worker pulling off one queue. A crash or bad deploy in worker-webhooks never stops SLA escalation from running for every other customer; idempotency keys plus Service Bus session locks make a redelivered message a no-op instead of a duplicate.
worker-sla — SLA escalation worker-rules — business rules engine worker-webhooks — delivery + retries worker-reports — export scheduler worker-ai-agent — separate service, different resource profile
▼
⑦Monitoring & secrets
Azure Monitor and Application Insights feed the same health signals as Admin → System status, per worker, routed to PagerDuty. Key Vault holds DB passwords, API keys, and the Trakolo private key used to sign .trklic license files — never a plain .env in production.
Azure Monitor + Application Insights Alerts → PagerDuty, per worker Key Vault — secrets
Layer-by-layer: AWS vs. Azure
LayerAWS referenceAzure equivalentWhy it's a drop-in swap
EdgeRoute 53, ACM, ALB/CloudFrontAzure DNS, Front Door (managed TLS + WAF)Both resolve a subdomain, terminate TLS, and route to the app fleet — no app code touches this layer.
API GatewayAmazon API GatewayAzure API ManagementBoth handle routing, auth, per-tenant rate limiting, versioning, and publish a developer portal — the API contract doesn't change, only which managed gateway enforces it.
App fleetECS Fargate / EKSContainer Apps (or AKS) + Static Web AppsContainer Apps auto-scales on HTTP/CPU load the same way Fargate does — the ASP.NET Core 8 API image doesn't change.
Control planeElastiCacheAzure Cache for RedisSame Redis protocol — the trakolo-master cache client code is identical either way.
Data tierRDS Postgres Multi-AZ + read replica, S3Flexible Server (zone-redundant HA) + read replica, Blob StorageBoth are managed Postgres with automated failover and backups — db/schema.sql runs unmodified per tenant database on either.
Background services5 separate ECS services (sla, rules, webhooks, reports, ai-agent), each SQS-backed or Postgres-backed5 separate Container Apps jobs, each on its own Service Bus queueWorkers only need a queue to pull from — the job-processing code, including the idempotency-key check, is cloud-agnostic per worker.
MonitoringCloudWatch / Datadog → PagerDutyAzure Monitor + Application Insights → PagerDutyBoth ingest the same per-worker health signals already shown in Admin → System status.
SecretsSecrets ManagerAzure Key VaultDB passwords, API keys, and the license-signing key are read at boot from a managed vault either way — never committed, never in a plain .env in production.
The only layer where the two clouds genuinely diverge in behavior is Front Door vs. ALB/CloudFront — Front Door bundles CDN, WAF, and global load balancing in one resource, where AWS splits that across two or three. Everything else is a like-for-like managed-service swap; the same shape maps onto Cloud SQL/Memorystore/GCS on GCP too.

Domain and database — there isn't a Trakolo-managed one
Every cloud tenant gets a *.trakolo.com subdomain resolved to its dedicated database through trakolo-master's tenant registry (see Application architecture). A standalone install has neither: core.tenants.subdomain, db_host, and db_name are all NULL for a standalone row — enforced by a check constraint in db/schema-master.sql, not left to convention. The customer points whatever hostname their own network uses (an internal DNS entry, a bare IP, a VPN-only address) at the container — Trakolo neither hosts nor routes to it. trakolo-master keeps that tenant's row only for licensing: install_contact_email and last_license_checkin_at, updated each time .trklic validates, are the only signal that ever comes back — never a live connection.
License activation
A workspace's .trklic file — a JSON payload signed with Trakolo's private key — is issued whenever seats, modules, or the expiry date change, and verified locally against the public key bundled with the install. Air-gapped networks activate offline: License → Offline activation generates a request code, exchanged for a response code on the customer portal from any machine with outbound access, then pasted back in. See site/docs.html for the full walkthrough.
